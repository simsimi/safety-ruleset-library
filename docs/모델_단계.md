# 모델 단계 (분류모델 어댑터·정책·통합 평가)

사전 단계 뒤에 붙는 분류모델 단계의 연결 방식과 채점 규칙이다.

## 기본 모델

- 기본 구성은 **사전 단계 + 위해 모델 단계 + 감정 모델 단계**이며, 세 단계 모두 기본 제공된다.
- 기본 위해 모델은 **진성/비진성 판별 모델**이다 — 백본은 KcELECTRA-base(`beomi/KcELECTRA-base-v2022`)이며, 발화의 위해 진성 여부를 확률로 판별한다.
- 기본 감정 모델은 **우울/불안 판별 모델**이다 — 백본은 KoELECTRA-small(`monologg/koelectra-small-v3-discriminator`)이며, 감정 헤드의 우울·불안 확률을 낸다.
- `--model-config`와 `--harm-model-config`를 지정하지 않고 실행하면 기본 모델 설정(`models/default-emotion.yaml`, `models/default-harm.yaml`)이 자동 적용된다. 모델 파일이 준비되지 않은 단계는 건너뛰며, 감정 모델이 없으면 경고가 출력된다.
- 모델 가중치는 저장소에 직접 넣지 않고 배포 자산으로 제공한다. `python3 tools/download_models.py`로 내려받아 `models/` 아래에 배치한다.
- 본 프로젝트의 범위는 기본 모델과 어댑터를 제공하며, 파인튜닝된 모델을 이용해 위험판정 성능을 테스트할 수 있다. 모델별 상세는 함께 제공되는 모델 문서를 참고한다.

## 역할 분리

- **어댑터**는 발화를 받아 점수만 돌려준다: `{depression, anxiety, else}` (각 0..1, else가 없으면 1-우울-불안으로 채운다).
- **판정(임계값 적용)은 채점 단계의 정책**이 한다. 그래서 모델 실행 결과(`predictions.jsonl`의 model 행, `predicted: null` + `scores`)를 저장해 두면, 임계값을 바꿔도 모델을 다시 부르지 않고 재채점만으로 결과를 얻을 수 있다.
- 모델 호출 오류는 행에 `error`로 남기고 지표 분모에서 제외한다.

## 어댑터 종류 (설정 YAML의 `adapter`)

| 종류 | 용도 | 설정 |
|---|---|---|
| `http` | 별도 서버로 띄운 모델 (로컬 모델 서버, API 기반 모델) | `http.url`, `timeout`, `response_map`(응답 경로 점 표기), `api_key_env`(환경변수에서 Bearer 키) |
| `file` | 로컬 모델을 오프라인으로 돌려 만든 점수 파일 연결 | `file.path` (JSONL: `{"id" 또는 "text", "scores": {...}}`) |
| `local` | 로컬 모델 파일 직접 실행 (ONNX 또는 HuggingFace) | `local.path`, `format`(auto/onnx/hf), `label_map`, `class_labels`(ONNX용), `max_length`(입력 절단 토큰 수 — 모델 학습 시 절단 길이와 맞출 때 지정) |
| `stub` | 데모용 규칙 스텁 — **실제 모델이 아니다** | 없음 |

설정 예시는 `models/example-http.yaml`, `models/example-local.yaml`, 데모 실행은 `models/stub.yaml`을 참고한다.

### 기본 모델 셋업

기본 모델 가중치는 배포 자산(zip)으로 제공된다. 기본 모델 두 개의 구조·학습 데이터·평가 결과는 [기본 모델 기술 문서](model-documentation.pdf)에 기술되어 있다.

```bash
pip install -e ".[local-hf]"
python3 tools/download_models.py   # models/emotion-heads-v1/, models/harm-genuine-v2/ 배치
riskcheck evaluate --dataset data/evalset_human.jsonl --dict dicts/default.yaml \
    --out runs/base
```

- 모델을 지정하지 않으면 기본 모델 설정 두 개가 자동 적용돼 사전+위해 모델+감정 모델 전체 구성으로 평가한다.
- 모델 가중치 디렉터리(`models/emotion-heads-v1/`, `models/harm-genuine-v2/`)는 git에 넣지 않는다 — 다운로드 스크립트로 내려받는다.

### 기본 모델을 자기 모델로 교체하기

기본 모델은 출발점이다. 자기 안전진단 모듈을 점검하려면 모델을 교체한다.

1. **연결 방식을 고른다.** 로컬 파일(ONNX/HuggingFace)이면 `local`, 별도 서버로 띄운 모델이면 `http`, 미리 계산한 점수 파일이면 `file` 어댑터를 쓴다 (위 어댑터 표 참고).
2. **설정 파일을 만든다.** 기본 설정을 복사해 출발점으로 삼는 것이 빠르다 — 감정 모델은 `models/default-emotion.yaml`, 위해 모델은 `models/default-harm.yaml`을 복사한다. 바꿀 곳은 `local.path`(자기 모델 디렉터리)와 출력 선언이다. 감정 모델은 모델이 내는 출력에서 우울·불안 점수를 어디서 읽을지(`outputs`의 `from`/`activation`)를 자기 모델 구조에 맞게 고치고, 위해 모델은 위해 확률을 읽는 위치(`harm_output`)를 고친다. 모델 구조가 단순한 다중클래스 분류기면 `models/example-local.yaml`의 `label_map` 방식이, 서버 연결이면 `models/example-http.yaml`이 출발점이다.
3. **지정해서 실행한다.**

   ```bash
   riskcheck evaluate --dataset data/evalset_human.jsonl --dict dicts/default.yaml \
       --model-config my-emotion.yaml --harm-model-config my-harm.yaml \
       --out runs/mine
   ```

   한쪽만 교체할 수도 있다. 지정하지 않은 쪽은 기본 모델이 자동 적용된다.
4. **결합 정책과 임계값을 조정한다.** 위해 결합은 설정 파일의 `policy`(`confirm`/`standalone`)나 CLI `--harm-confirm`/`--harm-standalone`으로, 감정 임계값은 설정 파일의 `thresholds`나 CLI `--threshold-depression`/`--threshold-anxiety`로 바꾼다.
5. **단계만 바꿔 다시 평가한다.** 단계 결과는 `predictions.jsonl`에 분리 보관되므로, 모델 하나만 교체하면 그 단계의 결과 파일만 갈아 끼워 재채점할 수 있고, 임계값·정책만 바꿀 때는 모델을 다시 부르지 않고 `--predictions`로 재채점만 하면 된다.

### 로컬 어댑터 계약: 선언과 변형 규칙

연결은 두 층으로 나뉜다.

- **출력 선언** — 모델이 무엇을 내는지를 선언한다. HuggingFace 모델은 모델 자체의 `id2label`이 선언이고, ONNX 모델은 설정의 `class_labels`에 출력 순서대로 이름을 적어 선언한다.
- **변형 규칙** — 선언된 출력을 어떻게 변형/계산해서 이 도구가 요구하는 `{depression, anxiety, else}` 점수로 바꿀지를 정한다. 모델 형태에 따라 두 가지다.

변형 규칙:

- `label_map` (단일 softmax 분류기용): 전체 출력에 softmax를 걸고 지정 클래스를 합산한다. 값은 클래스 이름이나 인덱스이며, 목록으로 주면 합산한다 — 게이트형 4분류(우울/불안/기타부정/평온) 모델은 `else: [기타부정, 평온]`처럼 합쳐 연결할 수 있다. 지정이 없으면 클래스 이름에서 depression/anxiety/else를 찾고, 없으면 인덱스 0/1/2로 본다.
- `outputs` (복합 출력 모델용): 점수 키마다 출처(`from`)와 변환(`activation`), 조합법(`combine`)을 지정한다. `activation`은 `softmax`(전체 또는 `group` 멤버 안에서), `sigmoid`(출력별 독립), `none`(모델이 이미 확률을 낼 때) 중 하나다. `from`이 여러 개면 활성화한 값들을 `combine`으로 합친다 — `sum`(기본, 확률 합산), `max`(가장 강한 신호), `mean`(평균). 둘 다 있으면 `outputs`가 우선한다.
- 추가 의존성이 필요하다: ONNX는 `pip install -e ".[local-onnx]"`, HuggingFace(PyTorch)는 `pip install -e ".[local-hf]"`. 기본 설치에는 포함되지 않는다.

### 모델 형태별 연결

실무 분류모델은 출력 구조가 제각각이라, 형태에 맞는 연결법을 고른다. 어느 쪽이든 riskcheck 쪽 판정·재채점 구조는 그대로다.

| 모델 형태 | 연결 | 방법 |
|---|---|---|
| 단일 다중클래스 (softmax) | local + `label_map` | 클래스 이름/인덱스를 우울·불안·else에 대응 (`models/example-local.yaml`) |
| 멀티라벨 (클래스별 sigmoid 헤드) | local + `outputs` | 우울·불안 헤드를 `activation: sigmoid`로 지정 (`models/example-local-multihead.yaml`) |
| 게이트 + 헤드 혼합 (softmax 그룹 + sigmoid) | local + `outputs` | 헤드는 sigmoid, 게이트 쪽 점수는 `group` 멤버 안에서 softmax해 합산 (같은 예시 파일). 헤드 기준으로 연결한 실제 모델 설정은 `models/default-emotion.yaml` (기본 감정 모델) |
| 프레임워크 무관 (점수만 뽑을 수 있으면 됨) | file | 발화별 점수를 JSONL로 만들어 넘긴다: `{"id": ..., "scores": {"depression": .., "anxiety": ..}}` |
| 서빙 중인 모델 | http | `{"text": ...}` POST에 점수 JSON을 돌려주는 엔드포인트. 응답 필드가 다르면 `response_map`으로 지정 |

주의: 멀티라벨·혼합 모델을 `label_map`으로 연결하면 전체 출력에 softmax를 거는 셈이 되어, 모델이 검증된 확률과 다른 점수가 된다. 헤드가 sigmoid인 모델은 반드시 `outputs`로 연결할 것.

## 위해 모델 (옵션)

감정 모델과 별개로, 위해(자살·자해 진성) 확률을 내는 모델을 두 번째 슬롯에 연결할 수 있다. `--harm-model-config`로 지정하며, 지정하지 않으면 위해 모델 없이 동작한다.

- 계약: 어댑터는 발화별 **위해 확률 하나(`harm`, 0~1)** 를 돌려준다. 어댑터 종류는 감정 모델과 같다(http·file·local·stub).
- 로컬 연결: 설정 `local.harm_output`으로 어느 출력이 위해 확률인지 선언한다. 형식은 `outputs` 스펙과 같다 — `{from: 이름|인덱스, activation: softmax|sigmoid|none, group: [...], combine: sum|max|mean}`. 이진 분류기(비진성/진성)면 `from: <진성 클래스>`, `activation: softmax`, `group: [양쪽 클래스]`가 표준이다 (`models/example-harm-local.yaml`).
- 파일 연결: 점수 파일 행에 `{"id": ..., "harm": 0.83}` 또는 `{"id": ..., "scores": {"harm": 0.83}}` 형식으로 둔다.
- 결합 정책 (`policy`): `confirm`은 사전이 잡은 건을 `risk`로 확정하는 데 필요한 위해 확률(기본 0.5), `standalone`은 사전이 놓친 건을 위해 모델 단독으로 `risk`로 올리는 위해 확률(기본 0.4)이다. 설정 파일 `policy`나 CLI `--harm-confirm/--harm-standalone`으로 바꾼다. `confirm: 0`이면 사전 판정을 그대로 확정하고(사전 우선 결합), `standalone`을 1보다 크게 두면 단독 승격이 꺼진다(순수 확인형 결합).
- 위해 모델 단독 리포트는 `report_harm.json`으로 나오며, 본 지표는 `standalone` 운용점 기준이고 `confirm` 운용점 지표(`harm_confirm_metrics`)를 함께 기록한다.
- 위해 모델 오류 건은 위해 결합을 건너뛰고 기존 규칙(사전 + 감정 신호)으로 평가한다.

## 정책과 통합 판정

- 모델 판정: `depression ≥ 임계값` 또는 `anxiety ≥ 임계값`이면 신호 있음. 기본 임계값은 둘 다 0.5이며, 설정 파일 `thresholds`나 CLI `--threshold-depression/--threshold-anxiety`로 바꾼다.
- 마진 정책: 설정 파일 `thresholds.margin`(또는 CLI `--margin`)을 주면, 임계값을 넘는 신호라도 `else`보다 margin 이상 크지 않으면 신호로 보지 않는다. 변형 규칙에서 `else`를 '평온'으로 선언한 게이트형 모델이 "부정이 평온보다 일정 이상 높을 때만 부정"으로 판정하는 방식을 재현하는 옵션이다.
- 판정은 위험/비위험 이진이라, 모델 신호가 있으면 `risk`로 판정한다.
- 통합 규칙: 위해 모델이 없으면 사전 판정이 `risk`면 그대로 두고, 사전이 `none`인 경우에만 감정 모델 신호로 `risk`까지 올린다. 위해 모델이 있으면 먼저 위해 결합(사전 판정 × 위해 확률, `confirm`/`standalone` 정책)을 적용하고, 거기서 `risk`가 되지 않은 건을 감정 모델 신호로 올린다. 어느 모델이든 오류 건은 해당 결합을 건너뛴다.
- 리포트는 단계별로 나온다: `report_dict.json`(사전), `report_model.json`(감정 모델), `report_harm.json`(위해 모델, 연결한 경우), `report_combined.json`(통합). 재채점은 `--predictions <기존 predictions.jsonl>`로 실행 없이 수행한다.

## 해석 주의 (스텁 데모 실측 기준)

정답은 **자살·자해 위험**이고, 모델 단계가 재는 것은 **우울·불안 신호**다 — 서로 다른 구성개념이다. 그래서 모델 단계는 이진 판정 지표가 아니라 **하위 라벨 지표**로 평가한다 (하위 라벨 기준은 `docs/하위라벨_기준.md`).

스텁 데모 실측 (`examples/sample-report-balanced30/`, 대표 평가셋 500건, 임계값 0.5):

| 신호 | Precision | Recall | F1 | Support |
|---|---|---|---|---|
| 우울 | 0.8571 | 0.3529 | 0.5000 | 17 |
| 불안 | 1.0000 | 0.5500 | 0.7097 | 20 |
| 합산 | 0.9412 | 0.4444 | 0.6038 | 36 |

- 불안은 스텁의 키워드와 표현이 잘 맞아 그럴듯한 숫자가 나왔다. 놓친 건 "조마조마해", "안절부절" 같은 비키워드 표현이다.
- 우울 Recall이 낮은 건 스텁이 우울 **어휘**에만 의존하기 때문이다 — 우울 양성의 대부분은 자살 생각 진술과 완곡한 우울 표현이라 우울 단어가 없다. 의미 기반 모델이 필요한 지점이 그대로 드러난다.
- 통합(combined) 채점의 정답은 위해 라벨 또는 하위 라벨(우울/불안) 양성이다 — 단어에서 걸리면 경고, 우울/불안에 걸리면 주의로 보되 둘 다 위험 탐지로 치는 판정 규칙과 짝을 이룬다. 여기서 risk는 단계명이 아니라 보편적인 위험 탐지의 이진 정답이다. 하위 라벨이 없는 건은 위해 라벨만으로 정한다. 단계별 리포트(dict/harm/model)는 각 단계의 판정 대상만으로 채점한다.
- 실제 모델을 붙일 때는 이 어댑터로 연결하고, 임계값은 하위 라벨 지표로 정한다.
